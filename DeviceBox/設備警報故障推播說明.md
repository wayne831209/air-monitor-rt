# 設備警報與故障推播功能說明

## 功能概述

新增了設備警報和故障的 Teams 推播通知功能。當設備進入「警報」或「故障」狀態時，系統會自動發送 Teams 通知。

## 新增功能

### 1. 設備警報通知
當設備狀態變更為「警報」時，自動發送 Teams 通知。

**觸發條件**：
- 設備的警報 DI 訊號觸發
- 狀態從「正常」或「運轉」變為「警報」

**通知內容**：
```
⚠️ 設備警報

設備名稱: CO-32
狀態: 警報
時間: 2026-07-03 15:30:00
```

### 2. 設備故障通知
當設備狀態變更為「故障」時，自動發送 Teams 通知。

**觸發條件**：
- 設備的故障 DI 訊號觸發
- 狀態從任何狀態變為「故障」

**通知內容**：
```
🚨 設備故障

設備名稱: CO-32
狀態: 故障
時間: 2026-07-03 15:30:00
```

## 技術實作

### 1. TeamsNotificationService 新增方法

#### SendDeviceAlarmAsync
```csharp
public async Task SendDeviceAlarmAsync(string deviceName, string status)
```

**參數**：
- `deviceName` - 設備名稱（例如 CO-32）
- `status` - 狀態文字（警報）

**顏色**：橘色 (#FFA500)

#### SendDeviceFaultAsync
```csharp
public async Task SendDeviceFaultAsync(string deviceName, string status)
```

**參數**：
- `deviceName` - 設備名稱（例如 CO-32）
- `status` - 狀態文字（故障）

**顏色**：深紅色 (#DC143C)

### 2. MainForm 狀態追蹤機制

#### 狀態追蹤字典
```csharp
// 記錄每個設備的上次警報/故障狀態，避免重複推播
private Dictionary<string, string> lastDeviceAlertStates = new Dictionary<string, string>();
```

**Key**: 設備名稱（例如 "CO-32"）
**Value**: 狀態（"正常", "警報", "故障"）

#### 狀態檢查方法
```csharp
private void CheckAndNotifyDeviceStatus(string deviceName, bool isAlarm, bool isFault)
```

**功能**：
1. 檢查當前狀態
2. 與上次記錄的狀態比較
3. 如果狀態變更且進入警報/故障，發送通知
4. 更新狀態記錄

### 3. 整合到設備狀態檢測

#### 鑄造廠視圖
在 `UpdateAllFactories()` 中，處理每台空壓機狀態時：
```csharp
bool isAlarm = GetDIValue(modbus, compressor.IO.AlarmDI);
bool isFault = GetDIValue(modbus, compressor.IO.FaultDI);

// 檢查並發送設備狀態通知
CheckAndNotifyDeviceStatus(compressor.Name, isAlarm, isFault);
```

#### 其他廠域視圖
在 `GetCompressorStatuses()` 中，處理每台空壓機狀態時：
```csharp
bool isAlarm = GetDIValue(modbus, compressor.IO.AlarmDI);
bool isFault = GetDIValue(modbus, compressor.IO.FaultDI);

// 檢查並發送設備狀態通知
CheckAndNotifyDeviceStatus(compressor.Name, isAlarm, isFault);
```

## 通知邏輯

### 狀態變更檢測

```
[上次狀態] → [當前狀態] = [動作]

正常 → 警報 = 發送警報通知 ⚠️
正常 → 故障 = 發送故障通知 🚨
運轉 → 警報 = 發送警報通知 ⚠️
運轉 → 故障 = 發送故障通知 🚨
警報 → 故障 = 發送故障通知 🚨
警報 → 正常 = 不發送（狀態恢復）
故障 → 正常 = 不發送（狀態恢復）
警報 → 警報 = 不發送（避免重複）
故障 → 故障 = 不發送（避免重複）
```

### 防重複機制

1. **狀態追蹤**：記錄每個設備的上次狀態
2. **變更檢測**：只在狀態改變時發送通知
3. **冷卻時間**：TeamsNotificationService 內建 5 分鐘冷卻

## 配置需求

### 必要設定

1. **Teams Webhook URL**
   - 在 config.xml 或資料庫中設定
   - Power Automate 或 Teams Incoming Webhook

2. **通知啟用開關**
   - `config.TeamsNotificationEnabled = true`

3. **Email 通知對象**（選擇性）
   - 單一 Email：`user@example.com`
   - 多個 Email：`user1@example.com, user2@example.com`

### Config.xml 範例
```xml
<TeamsNotification>
	<Enabled>true</Enabled>
	<WebhookUrl>https://your-webhook-url</WebhookUrl>
	<NotificationEmail>user1@example.com, user2@example.com</NotificationEmail>
</TeamsNotification>
```

## 測試方式

### 1. 模擬警報狀態

**方法 A：修改 PLC 訊號**
1. 使用 PLC 工具設定警報 DI 為 ON
2. 等待程式更新（UpdateTimer 週期）
3. 檢查 Teams 是否收到通知

**方法 B：修改程式碼測試**
```csharp
// 暫時強制設定為警報狀態
bool isAlarm = true;  // 原本是 GetDIValue(...)
bool isFault = false;
```

### 2. 模擬故障狀態

**方法 A：修改 PLC 訊號**
1. 使用 PLC 工具設定故障 DI 為 ON
2. 等待程式更新
3. 檢查 Teams 是否收到通知

**方法 B：修改程式碼測試**
```csharp
// 暫時強制設定為故障狀態
bool isAlarm = false;
bool isFault = true;  // 原本是 GetDIValue(...)
```

### 3. 檢查 Debug 日誌

開啟 `debug_*.log` 檔案，搜尋關鍵字：

```
[推播] 設備狀態變更
[Teams通知] 設備警報通知已發送
[Teams通知] 設備故障通知已發送
```

### 4. 驗證狀態追蹤

**測試流程**：
1. 設備進入警報 → 應收到通知
2. 保持警報狀態 → 不應重複通知
3. 警報變故障 → 應收到故障通知
4. 保持故障 → 不應重複通知
5. 恢復正常 → 不發送通知
6. 再次進入警報 → 應收到通知

## 優點

### 1. 即時通知
- ✅ 設備異常立即通知
- ✅ 不需要人工監控

### 2. 智慧防重複
- ✅ 狀態追蹤避免重複通知
- ✅ 5 分鐘冷卻機制

### 3. 清楚識別
- ✅ 顯示具體設備名稱（CO-32）
- ✅ 不同狀態不同圖示和顏色

### 4. 完整記錄
- ✅ Debug 日誌追蹤
- ✅ Teams 通知歷史

## 注意事項

### 1. 冷卻時間
- 所有類型的通知共用 5 分鐘冷卻時間
- 避免短時間內大量通知

### 2. 狀態恢復
- 設備恢復正常時**不發送通知**
- 避免過多訊息干擾

### 3. 初始狀態
- 程式啟動時，所有設備初始化為「正常」
- 第一次檢測到警報/故障會發送通知

### 4. 網路需求
- 需要能連接到 Teams Webhook URL
- 網路異常時通知會失敗（不影響程式運行）

## 疑難排解

### 問題 1：沒有收到通知

**檢查清單**：
1. `config.TeamsNotificationEnabled` 是否為 `true`
2. Webhook URL 是否正確設定
3. 網路是否可連接到 Teams
4. 檢查 Debug 日誌是否有錯誤訊息

**Debug 日誌檢查**：
```
[Teams通知] Webhook URL 未設定  ← URL 沒設定
[Teams通知] 冷卻時間內，跳過通知  ← 太頻繁
[Teams通知] 發送設備警報通知失敗: xxx  ← 發送失敗
```

### 問題 2：收到重複通知

**可能原因**：
1. 狀態在正常和警報之間快速切換
2. 冷卻時間已過

**解決方式**：
- 檢查 DI 訊號是否穩定
- 考慮增加冷卻時間

### 問題 3：通知延遲

**原因**：
- UpdateTimer 週期（預設可能是 1-5 秒）
- 網路延遲

**正常延遲**：
- 1-10 秒內收到通知屬於正常
