# 推播路徑重構說明

## 問題描述

實際測試時發現推播功能仍使用舊版的 `OnPressureOverLimit` 和 `OnTempOverLimit` 方法，這些方法沒有實作新版的排程篩選和延遲機制。

## 問題根因

在 `UpdateAllFactories()` 更新 UI 時，每個工廠的空壓/溫度標籤會透過以下路徑觸發推播：

```
UpdateAllFactories()
  └─> UpdatePressureLabelWithLimitCheck() / UpdateTempLabelWithLimitCheck()
	  └─> OnPressureOverLimit() / OnTempOverLimit()  ← 舊版推播路徑
```

這導致：
1. **推播被觸發兩次**（UI 更新時一次 + 背景監控一次）
2. **舊版推播沒有排程篩選**：所有設備都會推播，不管是否有排程
3. **舊版推播沒有延遲機制**：不符合 `alarm_delay_minutes` 設定
4. **無法統一管理**：推播邏輯分散在兩個地方

## 解決方案

### 1. 移除 UI 更新路徑的推播呼叫

修改 `UpdatePressureLabelWithLimitCheck()` 和 `UpdateTempLabelWithLimitCheck()`：

**修改前：**
```csharp
if (overLimit)
{
	UpdateLabel(label, valueText, StatusOverLimit);
	string source = string.IsNullOrEmpty(deviceName) ? label.FindForm()?.Text : deviceName;
	OnPressureOverLimit(source, valueText, limits);  // ← 舊版推播呼叫
}
```

**修改後：**
```csharp
if (overLimit)
{
	UpdateLabel(label, valueText, StatusOverLimit);
	// 推播通知由 MonitorAllDevicesInBackground() 統一處理
}
```

### 2. 標記舊方法為過時

將 `OnPressureOverLimit()` 和 `OnTempOverLimit()` 標記為 `[Obsolete]`，並清空內容，只保留警告訊息：

```csharp
[Obsolete("推播已改由 MonitorAllDevicesInBackground() 統一處理")]
private void OnPressureOverLimit(string source, string currentValue, AlarmLimitsConfig limits)
{
	System.Diagnostics.Debug.WriteLine($"[警告] OnPressureOverLimit 已廢棄，推播應由 MonitorAllDevicesInBackground() 處理");
}
```

### 3. 推播統一由背景監控處理

所有推播邏輯現在統一由 `MonitorAllDevicesInBackground()` 處理：

```
MonitorAllDevicesInBackground()
  └─> 遍歷所有工廠和設備
	  ├─> GetScheduledCompressorIds()  ← 篩選有排程的設備
	  ├─> 檢測異常（空壓、溫度、警報、故障）
	  ├─> 記錄異常開始時間（abnormalStartTimes）
	  ├─> 檢查是否超過延遲時間（alarm_delay_minutes，僅空壓溫度）
	  └─> SendCombinedAbnormalNotification()  ← 統一推播
```

## 修改後的行為

### UI 更新路徑（不再推播）
- `UpdatePressureLabelWithLimitCheck()` / `UpdateTempLabelWithLimitCheck()`
- **只負責**：更新 Label 文字和顏色
- **不再負責**：推播通知

### 背景監控路徑（統一推播）
- `MonitorAllDevicesInBackground()`
- **負責**：
  - 監控所有工廠的所有設備
  - 篩選有排程的設備
  - 記錄異常開始時間
  - 套用延遲機制（僅空壓溫度）
  - 統一批次推播

## 新版推播特性

✅ **排程篩選**：只推播有排程運行的設備  
✅ **延遲機制**：空壓/溫度超限需持續 `alarm_delay_minutes` 才推播  
✅ **立即推播**：設備警報/故障立即推播（不延遲）  
✅ **批次推播**：同一次檢測的所有異常合併成一則訊息  
✅ **冷卻時間**：推播間隔受 `notification_cooldown_minutes` 控制  
✅ **資料庫驅動**：所有設定都儲存在 `notification_settings` 表中

## 測試建議

1. **確認推播不重複**：同一個異常應該只推播一次
2. **確認排程篩選有效**：沒有排程的設備不應推播
3. **確認延遲機制有效**：空壓/溫度超限需持續設定的分鐘數才推播
4. **確認警報立即推播**：設備警報/故障應該立即推播
5. **確認批次推播**：多個異常應該合併成一則訊息
